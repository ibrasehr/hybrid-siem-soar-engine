# hybrid-siem-soar-engine
Python-based next-gen SIEM/SOAR platform featuring hybrid ML correlation, UEBA insider threat detection, governed automated response with transactional rollback, and explainable AI traces.

## Correlation Engine & Offline Pipeline

The correlation module combines a Random Forest classifier with behavioral rule tracing, target leakage protection, threshold sweeping, drift testing, and schema-validated JSON alert generation.

### Installation

1. Create and activate a Python virtual environment:
```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

2. Install dependencies:
```powershell
pip install -r requirements.txt
```

### Training & Running the Offline Evaluation Pipeline

Run the end-to-end evaluation benchmark (multi-seed threshold sweep, speed benchmark, and leave-one-family-out drift test):

```powershell
.\.venv\Scripts\python.exe correlation_pipeline.py --csv data/UNSW_NB15_training-set.csv --label-col attack_cat --benign Normal
```

With feature ablation (e.g., dropping synthetic testbed artifacts):
```powershell
.\.venv\Scripts\python.exe correlation_pipeline.py --csv data/UNSW_NB15_training-set.csv --label-col attack_cat --benign Normal --ablate sttl,ct_state_ttl,ct_dst_src_ltm
```

### Running the CorrelationEngine CLI

Train the `CorrelationEngine` and evaluate events to produce schema-validated JSON Lines alerts:

```powershell
.\.venv\Scripts\python.exe correlation_engine.py --train-csv data/UNSW_NB15_training-set.csv --input-csv data/UNSW_NB15_training-set.csv --threshold 0.5 --out alerts.jsonl
```

### Running Tests

Execute the automated test suite with pytest:
```powershell
.\.venv\Scripts\python.exe -m pytest -v tests/test_engine.py
```

### Output Files

- `results/threshold_results.csv`: Single-seed threshold sweep metrics (recall, FPR, precision) for both the rule baseline and Random Forest.
- `results/threshold_multiseed.csv`: Multi-seed threshold sweep metrics reporting mean and standard deviation across seeds.
- `results/drift_results.csv`: Leave-one-family-out evaluation metrics across unseen attack families.
- `results/speed_results.csv`: Inference throughput (events/sec) and latency across batch sizes (100, 1,000, 10,000).
- `results/ablation_*.csv`: Corresponding evaluation outputs when running with `--ablate`.
- `schema.json`: Formal JSON Schema defining the required structure for incident alerts.
- `sample_alert.json`: Representative schema-compliant incident alert record with feature importance tracing and fired behavioral rules.
- `alerts.jsonl`: Line-delimited JSON alerts generated by the `CorrelationEngine` CLI.

### Alert Schema & Field Reference (`alerts.json`)

`alerts.json` contains representative incident alerts formatted according to `schema.json`:

- `incident_id`: Unique identifier string formatted as `INC-` followed by the zero-padded event index.
- `confidence`: Confidence score representing the Random Forest posterior attack probability rounded to 4 decimals (range 0.0 to 1.0).
- `contributing_event_ids`: List of integers representing contributing event IDs. Currently contains a single event ID per alert as multi-event incident grouping is not implemented yet.
- `time_window`: Object containing `start`, `end`, and `basis` fields. Set to `{"start": <id>, "end": <id>, "basis": "row_index"}` because the benchmark dataset lacks absolute timestamps; timestamps are deliberately not fabricated.
- `trace`: Explainable AI diagnostic trace object:
  - `model`: Name of the scoring model (`"random_forest"`).
  - `threshold`: Operating classification threshold (`0.5`).
  - `rules_fired`: List naming all hand-written behavioral rules that fired for this event (empty list `[]` if none).
  - `method`: Attribution method identifier (`"importance_x_zscore (heuristic local attribution, not SHAP)"`).
  - `top_features`: Top 5 contributing features ranked by global Random Forest importance multiplied by the absolute z-score versus benign training traffic. Each item contains `feature`, `importance`, `observed_value`, and `z_score`.
- `ground_truth_family`: Dataset ground-truth attack category (`attack_cat`), retained strictly for offline evaluation and benchmark analysis (marked `evaluation_only` in `schema.json`).

### Limitations

1. **Benchmark Split**: The evaluation is evaluated using stratified train/test splits on a single benchmark dataset (`UNSW_NB15_training-set.csv`). Real-world enterprise traffic may exhibit time-series dependencies and higher distribution shift.
2. **Speed Measurement Scope**: The speed benchmark measures model scoring and inference throughput in memory only (`predict_proba`). It does not measure end-to-end network packet capture, stream ingestion, feature computation, or disk persistence overhead.
3. **Rule Baseline Implementation**: The rule baseline consists of 5 hand-written domain-specific threshold rules fitted to the 99th percentile of benign training traffic, rather than a full stateful Wazuh SIEM engine or its complete production XML ruleset.
4. **Time Window & Incident Grouping**: The `time_window` is strictly row-index based (`"basis": "row_index"`) due to the absence of packet timestamps in the training set. Incident correlation/grouping across multiple events into a single incident is not implemented.

## SOAR Response Engine & Dashboard

Governed response layer that consumes the correlation engine's alerts (`alerts_full.jsonl` or the `alerts.json` sample) and decides what to do with each one. Code is in `response_engine/`, the UI in `dashboard/`, and the tests in `tests/`.

### Installation

Uses the same virtual environment as above. `pip install -r requirements.txt` already includes the dashboard dependency (`streamlit>=1.49.0`; older versions fail because the dashboard uses `width="stretch"`).

### Decision Tiers

| Tier | Condition | Action |
|------|-----------|--------|
| `LOG_ONLY` | confidence < 0.50 (review floor) | Recorded only, nothing executed |
| `REVIEW` | confidence < auto threshold (0.90), or held by the BDI gate | Analyst queue (capacity-limited, overflow is kept, never dropped) |
| `AUTO_SOFT` | 0.90 <= confidence < 0.97 | `rate_limit_flow` / `step_up_mfa` |
| `AUTO_HARD` | confidence >= 0.97 (hard threshold) | `block_flow` / `suspend_session` |

All thresholds, the BDI limit and the queue capacity are set in one validated `Policy` object (`response_engine/policy.py`).

### Safety Mechanisms

- **Business Disruption Index (BDI) gate**: BDI = asset criticality (1-5) x action severity (soft 2, hard 5). An automatic action whose BDI exceeds the limit (default 12) is held for analyst approval even at high confidence.
- **Fixed action catalog**: only actions listed in `response_engine/catalog.py` can run; anything else raises `UnknownAction`.
- **Rollback ledger**: every executed action stores the prior state and its exact inverse; reverting verifies the restore and refuses (`StateDrift`) if the target changed in the meantime.
- **Explanations**: every decision carries a plain-language reason built from the correlation trace (rules fired, top features).
- **Feedback log**: analyst approvals, rejections and reverts are recorded. `suggest_threshold()` only suggests a value and never applies it.
- **Fail closed**: a missing, NaN or out-of-range confidence raises an error instead of triggering an action.
- Decisions never read ground truth; `ground_truth_family` is used only to score results.

### Generating the Evaluation Alerts (held-out split)

`--eval-split` scores only the held-out 30% of events. Pass `--alerts-json` a scratch path, otherwise the committed `alerts.json` is overwritten:

```powershell
.\.venv\Scripts\python.exe correlation_engine.py --train-csv data/UNSW_NB15_training-set.csv --eval-split --threshold 0.5 --alerts-json scratch/sample.json --alerts-full data/alerts_full.jsonl
```

### Running the Threshold Sweep

```powershell
.\.venv\Scripts\python.exe -m response_engine.evaluate data/alerts_full.jsonl
.\.venv\Scripts\python.exe -m response_engine.evaluate data/alerts_full.jsonl --no-bdi-gate --out results/sweep_no_gate.csv
```

Results are written to `results/response_threshold_sweep.csv` (auto-response rate, auto precision, false auto-actions, attacks waiting in review, per threshold).

### Running the Dashboard

```powershell
.\.venv\Scripts\python.exe -m streamlit run dashboard/app.py
```

The dashboard loads `data/alerts_full.jsonl` if present, otherwise the `alerts.json` sample (or upload a file in the sidebar). It shows the decision log, analyst review queue, rollback ledger, feedback log and audit export.

### Running All Tests

```powershell
.\.venv\Scripts\python.exe -m pytest -v tests/
```

`tests/test_engine.py` covers the correlation engine; the remaining test files cover the response engine.

### Response Engine Limitations

1. **Simulated actions**: actions change an in-memory state model; no real firewall or identity-provider calls are made.
2. **No host data**: the alerts carry no host/IP, so actions target the flow itself (`flow-<event_id>`).
3. **Simulated asset criticality**: criticality is derived from a stable hash of the target (replace it with `AssetRegistry.from_csv(...)` for a real inventory), so BDI figures illustrate the mechanism, not a real environment.
4. **Biased sample**: `alerts.json` holds 50 highest-confidence plus 50 random alerts. Use `alerts_full.jsonl` for any reported numbers.
5. **One active containment per target**, and the feedback loop stops at logging plus a threshold suggestion; automatic retraining is future work.

## Insider Threat Detection Module

UEBA behavioral anomaly detection module (`insider_threat_engine.py`) combining a pre-trained Random Forest classifier (`models/insider_threat_model.pkl`) with per-user behavioral rule checks on CERT-style activity logs.

### Features & Behavioral Rules

`InsiderThreatEngine.build_features(events)` aggregates raw activity logs (`event_id`, `timestamp`, `user`, `event_type`) per user into 9 features (`total_events`, `http_count`, `device_count`, `email_count`, `logon_count`, `file_count`, `after_hours_count`, `weekend_count`, `active_days`).

`InsiderThreatEngine.predict(events)` emits `source = "insider_threat"` (matching `response_engine/catalog.py` actions `step_up_mfa` / `suspend_session`), Random Forest attack probability (`confidence`), `predicted_label`, and `apply_rules()` flags:

- `High event volume` (`total_events >= 100`)
- `Excessive web activity` (`http_count >= 100`)
- `Unusual device usage` (`device_count >= 5`)
- `Excessive file activity` (`file_count >= 3`)
- `Unusual after-hours activity` (`after_hours_count > 6`, outside 08:00–18:00)

### Artifacts & Dashboard

- `models/insider_threat_model.pkl` & `models/insider_threat_features.pkl`: Serialized Random Forest classifier and expected feature column list.
- `data/insider_threat_predictions.csv`: SOAR-compatible prediction table (`id`, `source`, `confidence`, `true_label`) consumable by `response_engine.load_insider_csv()`.
- `data/insider_threat_alerts.json`: Precomputed alert records rendered on the **Insider Threat** Streamlit page (`dashboard/pages/2_Insider_Threat.py`), which also supports live CSV upload (`event_id`/`id`, `timestamp`, `user`, `event_type`/`file`).
